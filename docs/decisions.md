# Принятые решения

Краткий журнал: что решили и почему. Дополняется по ходу работы.

1. **Три сервиса, три базы в одном контейнере Postgres.** Сервис владеет своими данными и видит только свою базу (право CONNECT у PUBLIC отозвано). Один контейнер экономит память на локальной машине.
2. **Миграции Flyway в каждом сервисе.** У сервиса своя база и своя история миграций, он разворачивается независимо. Hibernate работает в режиме `validate`, схему не меняет.
3. **Нет внешних ключей между базами.** Идентификаторы других сервисов хранятся как обычные UUID.
4. **Идемпотентность на трёх уровнях** (расширено до четырёх в п. 13).
   - клиент → transfer-service: `UNIQUE (initiator_id, idempotency_key)` в `transfers`;
   - transfer-service → account-service: `UNIQUE (transfer_id, type)` в `account_transactions`;
   - Kafka → notification-service: `UNIQUE (source_event_id)` в `notifications`.
5. **Перевод выполняется одной локальной транзакцией в account-service**, чтобы не требовались распределённые транзакции. transfer-service оркестрирует и хранит статус.
6. **Transactional outbox** для публикации событий: событие пишется в `outbox_events` в той же транзакции, что и изменение перевода, и отправляется в Kafka отдельным процессом.
7. **Проводки и журнал аудита неизменяемы** (триггеры запрещают UPDATE/DELETE). Исправления делаются новыми записями.
8. **Деньги хранятся как `NUMERIC(19,4)`**, в коде это `BigDecimal`.
9. **Spring Boot 3.5.16** — последний релиз ветки 3.5 в open source. Переход на 4.x запланирован отдельной задачей.
10. **Один параметризованный Dockerfile** для всех сервисов (аргумент `MODULE`).
11. **Блокировки: пессимистичная основная, `@Version` страховка.** Все изменения баланса идут через `SELECT ... FOR UPDATE`: параллельные списания выстраиваются в очередь в БД, без повторных попыток. `@Version` оставлен на случай, если кто-то позже изменит баланс в обход блокировки: вместо тихой потери пополнения будет громкая ошибка. Перевод блокирует оба счёта одним запросом в порядке `id`: встречные переводы A→B и B→A не уходят в deadlock. `CHECK (balance >= 0)` в БД — последний рубеж.
12. **Идемпотентный повтор проверяется после блокировки счёта.** Иначе два одновременных вызова с одним ключом упёрлись бы в уникальный индекс с ошибкой 500. Семантика ответов: 201 — выполнено сейчас, 200 — повтор с теми же параметрами (сохранённый результат, деньги не двигаются), 409 — тот же ключ с другими параметрами. Для переводов ключ — `transferId`, который выдаёт transfer-service; для пополнений — заголовок `Idempotency-Key`.
13. **Идемпотентность пополнений — четвёртый уровень.** Заголовок `Idempotency-Key` обязателен (непустой, до 100 символов), уникален в пределах счёта (частичный уникальный индекс, миграция V3), допустим только у проводок `DEPOSIT`. Обязательность выбрана, чтобы не оставлять незащищённый путь: повтор после таймаута клиента не пополнит счёт дважды. Проводки переводов защищены `UNIQUE (transfer_id, type)`.
14. **Временные сбои конкуренции — 503 + `Retry-After: 1`.** Таймаут блокировки, deadlock и конфликт версий возвращают коды `RESOURCE_BUSY` и `CONCURRENT_MODIFICATION`. Операция при этом ничего не изменила, поэтому повтор с тем же ключом безопасен. Единое правило для клиента: «503 = повтори». 409 остаётся только за конфликтом параметров (`TRANSFER_CONFLICT`, `IDEMPOTENCY_KEY_REUSED`), он повтором не лечится. Ожидание блокировки ограничено `lock_timeout = 5s`, заданным через `spring.datasource.hikari.connection-init-sql`: это простая настройка, не зависящая от диалекта Hibernate; без неё запрос ждал бы блокировку бесконечно.
15. **Единый формат ошибок.** `ApiError { timestamp, status, code, message, violations[] }`. Обработчик наследуется от `ResponseEntityExceptionHandler`, чтобы стандартные ошибки Spring MVC (битый JSON, неверный UUID в пути, нет заголовка) оставались 4xx, а не превращались в 500. Ожидаемые бизнес-ошибки — наследники `ApiException` со своим статусом и кодом; непредвиденное — 500 `INTERNAL_ERROR`, детали только в логе.
16. **Защита внутреннего API `/internal/**` — общий секрет** в заголовке `X-Internal-Token` (переменная `INTERNAL_API_TOKEN`, при пустом значении приложение не стартует). Отдельная цепочка безопасности, публичное API не затрагивается; сравнение через SHA-256 и `MessageDigest.isEqual` (постоянное время), значение не логируется; для любой ошибки одинаковый 401, существование путей не раскрывается; пользовательский JWT доступа к `/internal` не даёт. Рассмотрены и отклонены:
    - только сетевая изоляция — порт account-service общий с публичным API, без шлюза `/internal` не спрятать;
    - пересылка пользовательского токена — позволяет вызвать `/internal` в обход transfer-service и его лимитов и проверок (проводки без записи о переводе и события), а фоновое добивание `PENDING` идёт без пользователя и токена (он живёт ~15 минут);
    - сервисный JWT, mTLS, OAuth2 client credentials через IdP — избыточны для пет-проекта; сервисный JWT — естественный путь развития, так как инфраструктура RS256 появится вместе с JWT.
    Владелец списываемого счёта проверяется по `initiatorId` из запроса (п. 25); сам `initiatorId` account-service получает от доверенного вызывающего сервиса.
17. **Разделение ответственности сервисов.** account-service — владелец балансов и проводок; проверка владельца счёта выполняется в нём (в той же транзакции и под блокировкой, без гонки «проверили — владелец сменился»). transfer-service — оркестрация: публичное API, идемпотентность клиента (ключ клиента → `transferId`), статус перевода, вызов account-service с повтором, добивание `PENDING`, outbox и события. Лимиты, холды и проверки (опциональные расширения) живут в transfer-service.
18. **Сущности и API account-service.** Связи с другими сущностями хранятся как `UUID`, без `@ManyToOne`: лишние join и ленивая загрузка в горячем пути не нужны, внешние ключи остаются в БД. Проводки и записи аудита помечены `@Immutable` и создаются фабричными методами, соблюдающими CHECK-ограничения. Запись аудита идёт в той же транзакции, что и операция (`Propagation.MANDATORY`).
19. **Суммы и пагинация.** Сумма: больше 0, до 15 цифр в целой части и до 4 в дробной; лишние знаки отклоняются с 400, не округляются молча. История операций: порядок «новые сверху» зафиксирован и совпадает с индексом, `page` и `size` приводятся к границам (`size` 1..100) вместо отказа, `sort` клиента игнорируется, наружу отдаётся собственный `PageResponse`.
20. **Тесты.** Интеграционные тесты идут на реальном Postgres (Testcontainers); один контейнер на прогон — бином в `@TestConfiguration`, а не статическим `@Container` (иначе кэшированный контекст ссылался бы на остановленный контейнер). Классы называются `*Test`: CI запускает `mvn verify` без Failsafe, `*IT` не выполнились бы. Проводки и аудит нельзя очистить (триггеры), поэтому каждый тест создаёт собственные данные. Гонки проверяются реально: 50 параллельных списаний, встречные переводы, одинаковые `transferId` и `Idempotency-Key`.
21. **Пул соединений.** HikariCP создаёт Spring Boot; `maximum-pool-size: 10` (значение по умолчанию) задан явно в `application.yml` account-service как документация и опора для тестов и будущей настройки под нагрузочный тест. Три сервиса по 10 соединений укладываются в `max_connections = 100` у Postgres.
22. **JWT: только access-токен, RS256, выдаёт account-service.** Claims: `sub` = `User.id`, `roles` (массив строк, превращается в `ROLE_*`), `iat`, `exp`; срок 15 минут (`app.jwt.access-token-ttl`). Refresh-токенов нет: для пет-проекта это лишнее состояние и поверхность атаки; клиент логинится заново. `/auth/register` сразу возвращает токен. Декодер жёстко привязан к RS256, поэтому `alg: none` и HS256 с публичным ключом в роли секрета отклоняются. Асимметричная подпись нужна, чтобы transfer-service проверял токены, имея только публичный ключ: утечка из него не позволяет выпускать токены. JWKS-эндпоинт не делаем: публичный ключ копируется файлом.
23. **Ключи JWT.** PEM-файлы: закрытый — PKCS#8, открытый — X.509, RSA не короче 2048 бит, пара обязана совпадать. Пути берутся из `JWT_PRIVATE_KEY_PATH` / `JWT_PUBLIC_KEY_PATH`, значений по умолчанию нет: без ключей приложение не стартует с понятным сообщением (fail-fast лучше, чем токены с «случайным» ключом после перезапуска). Бин `JwtKeyPair` с чтением файлов помечен `@Lazy` и в тестах заменяется `@Primary`-парой в памяти: тесты не зависят от файлов и от `.env`. Ключи создаёт `scripts/gen-keys.sh`, папка `keys/` в `.gitignore`. В Compose пути фиксированы (`/keys/...`), папка монтируется `:ro`; хостовые пути из `.env` в контейнер не попадают. `.env` Spring сам не читает, поэтому в `application.yml` есть `spring.config.import: optional:file:.env[.properties]`; формат `.properties` требует прямых слэшей в путях.
24. **Две цепочки безопасности и формат 401/403.** `/internal/**` — `@Order(1)`, секрет `X-Internal-Token`; остальное — `@Order(2)`, `oauth2ResourceServer` (JWT). Ошибки аутентификации и доступа отдаются как `ApiError`: 401 `UNAUTHORIZED` (+ `WWW-Authenticate: Bearer`), 403 `FORBIDDEN`. `/auth/register` и `/auth/login` публичные и игнорируют заголовок `Authorization` (собственный resolver токена): просроченный токен в браузере не должен мешать войти заново. Открытыми остаются только они и health/prometheus.
25. **Владение счётом.** Владелец берётся только из `sub`, `ownerId` в теле запроса не принимается. Чужой счёт — 403 `FORBIDDEN`, несуществующий — 404; существование проверяется первым. Утечка факта существования UUID допустима: UUID v4 не перебираются, а ответ «403» полезнее клиенту, чем маскировка под 404. Роль ADMIN обхода не даёт: проверка владельца едина для всех. Пополнить счёт может только владелец; проверка идёт под `FOR UPDATE` и раньше идемпотентного повтора (иначе чужой ключ раскрыл бы результат операции). Во внутреннем переводе `initiatorId` проверяется сразу после блокировки счетов, до поиска счёта получателя, проверки валюты и идемпотентного повтора. Ответ перевода содержит `fromOwnerId` и `toOwnerId` для notification-service.
26. **Аудит и действия пользователя.** `audit_log.actor_id` — пользователь (для переводов `initiatorId`); NULL только у системных действий. Добавлены действия регистрации и входа. `AuditService.record` работает с `Propagation.MANDATORY`: запись всегда в транзакции операции, а не «где-то рядом».
27. **Регистрация и вход.** Пароль хранится BCrypt-хэшем (`PasswordEncoder`). Длина 8–72 символа и не более 72 байт в UTF-8: BCrypt молча обрезает хвост, а это хуже явной ошибки. Несуществующий email и неверный пароль дают один и тот же 401 `INVALID_CREDENTIALS`, а при неизвестном email проверяется фиктивный хэш, чтобы время ответа не выдавало существование пользователя. Повторный email — 409 `EMAIL_ALREADY_REGISTERED`; гонку двух одновременных регистраций закрывает уникальный индекс по `lower(email)`, а не проверка в коде.
28. **Тесты безопасности.** Все интеграционные тесты наследуют `IntegrationTestBase` (`@Import` Postgres + `JwtTestConfig`): один кэшированный контекст и один контейнер на прогон. Помощники `bearer`, `expiredBearer`, `ownerBearer`, `ownerOf` выдают токены без похода в `/auth/login`. Быстрые тесты без контекста — разбор PEM, конвертеры, обработчики 401/403, `CurrentUser`. Исключение — `LockTimeoutTest` со своим контекстом.
29. **Redis убран из transfer-service, Kafka и `events-contract` оставлены.** Сейчас Redis негде применить. Кандидат на возвращение (возможное дальнейшее улучшение): лимиты переводов на пользователя (счётчики и rate limiting в transfer-service). Контейнер Redis в Compose остаётся в инфраструктуре; сам transfer-service его не использует и от него не зависит. Тесты на Kafka идут на Testcontainers; `spring-kafka` подключён в transfer-service (outbox), в notification-service подключается вместе с потребителем.
30. **Проверка JWT в transfer-service: только по публичному ключу.** `spring-boot-starter-oauth2-resource-server`, `NimbusJwtDecoder.withPublicKey(...)` с жёстко заданным RS256 (`alg: none` и HS256 отклоняются), `sub` = инициатор, `roles` превращаются в `ROLE_*`. Путь к ключу берётся из `JWT_PUBLIC_KEY_PATH`, значения по умолчанию нет: без него сервис не стартует с понятным сообщением. Бины на файлах `@Lazy`, в тестах заменяются `@Primary`-декодером с ключом в памяти. Закрытого ключа у сервиса нет: в Compose монтируется один файл `public.pem`, а не папка `keys`. Формат 401/403 тот же `ApiError`, что в account-service.
31. **Границы транзакций в transfer-service явные.** `TransferProcessor` сам не транзакционный и использует `TransactionTemplate`: короткая транзакция вставки `PENDING`; вызов account-service вне транзакции (соединение пула не занято на сетевом вызове); короткая транзакция финализации с `SELECT ... FOR UPDATE` и переходом только из `PENDING`. Вызов `process()` внутри транзакции запрещён (исключение), методы блокировки в репозитории требуют активной транзакции (`MANDATORY`). Это проверено тестами: во время вызова нет активной транзакции и занятых соединений Hikari. Сбой между вызовом и записью статуса закрывается повтором того же `transferId`: account-service идемпотентен.
32. **Клиент account-service.** `RestClient` с таймаутами (соединение 2 с, чтение 5 с), общий секрет в `X-Internal-Token` (`INTERNAL_API_TOKEN`, пустое значение останавливает старт, в логи не попадает). Повтор внутри одного вызова: до 3 попыток с паузой 200 мс и тем же `transferId` на 503, 5xx, таймаут и сетевую ошибку. Таблица исходов:
    - 201 и 200 → `COMPLETED`;
    - 404, 403, 422 (`ACCOUNT_NOT_FOUND`, `FORBIDDEN`, `INSUFFICIENT_FUNDS`, `CURRENCY_MISMATCH`, `SAME_ACCOUNT`) → `FAILED`, код ответа записывается в `failure_reason`;
    - 503, 5xx, сеть, таймаут после исчерпания попыток → перевод остаётся `PENDING`, клиенту 202;
    - 401, 400, 409 и любой неизвестный 4xx → перевод остаётся `PENDING`, клиенту 502 `UPSTREAM_ERROR` без деталей наружу. Это ошибка конфигурации или баг (секрет, формат запроса, `transferId` выдаёт сам transfer-service, поэтому 409 невозможен), а не отказ по существу, и объявлять такой перевод `FAILED` нельзя: деньги не двигались, но причина не бизнесовая.
    DTO внутреннего API продублированы в `transfer-service` (пакет `client`): общий модуль для двух records не нужен, а `events-contract` по правилам без логики и зависимостей не подходит.
33. **Идемпотентность клиента в transfer-service.** Ключ `Idempotency-Key` обязателен (непустой, до 100 символов) и уникален в пределах инициатора (`UNIQUE (initiator_id, idempotency_key)`). Сначала быстрый поиск, затем вставка; гонку двух запросов закрывает сам индекс: проигравший ловит `DataIntegrityViolationException`, читает победителя и действует как при обычном повторе. Ответы: 201 создан и обработан сейчас; 200 повтор с теми же параметрами (сохранённое состояние); 202 принят, account-service недоступен; 409 `IDEMPOTENCY_KEY_REUSED` другие параметры (сумма сравнивается по значению, `10.5` и `10.50` это один запрос); 422 `SAME_ACCOUNT` проверяется до обращения к БД; 502 `UPSTREAM_ERROR`. Повтор запроса для перевода в `PENDING` заново вызывает account-service с тем же `transferId` (решение пользователя): правило «202 значит повтори с тем же ключом» работает без ожидания фоновой задачи. Одновременные обработки одного перевода внутри одного экземпляра выстраиваются в очередь (`KeyedLock` на `ReentrantLock`, чтобы не приклеивать виртуальные потоки), поэтому параллельные запросы с одним ключом дают один вызов account-service. Между экземплярами такой защиты нет, и она не нужна: дубль вызова безвреден, статус ставится под `FOR UPDATE` из `PENDING`.
34. **`GET /transfers/{id}`.** Сначала 404 `TRANSFER_NOT_FOUND`, потом 403 `FORBIDDEN`; владелец это инициатор перевода, роль ADMIN обхода не даёт (то же правило, что в п. 25). Только чтение: без транзакции и без обращения к account-service.
35. **Фоновое добивание `PENDING`.** `@Scheduled`-проход (`SchedulingConfigurer`, пауза от конца предыдущего запуска) выбирает переводы старше `min-age` (60 с: заметно больше времени одного вызова), самые старые первыми, не больше `batch-size` (50), запросом с `FOR UPDATE SKIP LOCKED` в короткой транзакции, которая закрывается до сетевых вызовов. Затем каждый перевод обрабатывается тем же `TransferProcessor.process`, что и запрос клиента. От двойной обработки защищает идемпотентность account-service и финализация под `FOR UPDATE`, а `SKIP LOCKED` лишь не даёт экземплярам брать одну партию. При недоступности account-service проход прекращается (остальные упёрлись бы в тот же сбой и таймауты); ошибка одного перевода другие не останавливает. Выключатель `app.pending-retry.enabled` (`PENDING_RETRY_ENABLED`, по умолчанию включён); неверные значения останавливают старт, даже если задача выключена. Известное ограничение: перевод, стабильно получающий 502, попадает в каждую партию и при большом числе таких вытесняет более новые; для учебного сервиса принято.
36. **Данные transfer-service.** Сущность `Transfer` реализует `Persistable` с идентификатором, выданным приложением (иначе Spring Data делал бы лишний `SELECT` перед вставкой), связи хранятся как `UUID` без `@ManyToOne`, валюта `CHAR(3)` (`@JdbcTypeCode(SqlTypes.CHAR)`, иначе `ddl-auto: validate` падает), время `Instant` в `TIMESTAMPTZ` с усечением до микросекунд (ответ клиенту совпадает с тем, что потом прочитает `GET`). Смена статуса разрешена только из `PENDING`.
37. **Тесты transfer-service.** Один контекст и один контейнер Postgres на прогон (`IntegrationTestBase`). account-service подменён `MockRestServiceServer`, привязанным к `@Primary` `RestClient` в том же контексте (без второго контекста и без WireMock); ожидания нужно регистрировать до первого запроса, а не между ними. Реальный таймаут чтения проверен на JDK `HttpServer`. Ожидаемые `ERROR`-записи в логах тестов, которые намеренно провоцируют ошибки, не подавляются. Фоновое добивание в общем контексте выключено, а его логика проверяется прямым вызовом `runOnce()`. Классы называются `*Test`.
38. **Outbox: событие пишется в транзакции финализации и только при реальном переходе.** `TransferProcessor.finalizeTransfer` после `complete/fail` вызывает `OutboxWriter`, только если метод вернул `true`. Откат отменяет и статус, и событие. Второй обработчик (запрос клиента и фоновое добивание, два экземпляра) под `FOR UPDATE` видит финальный статус: перехода нет и события нет, поэтому на перевод приходится одно событие. `OutboxWriter` работает с `Propagation.MANDATORY` (как `AuditService`): вне транзакции падает, а не пишет «рядом». `outbox_events.id` это `event_id`, его выдаёт приложение (сущность `Persistable`, как `Transfer`); `aggregate_id` это `transferId`; `created_at` и `occurredAt` события это один момент по `Clock` с усечением до микросекунд. `payload` JSONB хранится строкой (`@JdbcTypeCode(SqlTypes.JSON)` и `columnDefinition = "jsonb"`, чтобы проверка схемы не зависела от диалекта), сериализует `ObjectMapper` Boot: время строкой ISO-8601. Тест проверяет, что в базе лежит JSON-объект, а не строка в кавычках (двойная сериализация). Миграция не понадобилась: таблица есть в V1.
39. **Контракт: в `TransferCompletedEvent` добавлено необязательное `toOwnerId`.** Notification-service нужен получатель, а владельца счёта зачисления знает только account-service (ответ содержит `fromOwnerId` и `toOwnerId`), в базе переводов его нет. Поле добавлено в конец record, как разрешает решение 9 (старые события читаются с `null`). `fromOwnerId` не добавлялся: счёт списания обязан принадлежать `initiatorId` (иначе account-service отвечает 403), то есть владелец списания всегда равен `initiatorId`. `TransferFailedEvent` не менялся: при отказе account-service владельцев не возвращает, поэтому об отказе уведомляется инициатор (`initiatorId`), а счета и сумма берутся из самого перевода, причина из `failure_reason`.
40. **Publisher: один проход в одной транзакции, отправка внутри неё.** Проход выбирает партию (`published_at IS NULL`, самые старые первыми, `FOR UPDATE SKIP LOCKED`, не больше `batch-size`), отправляет события по порядку, ждёт подтверждения (`send(...).get(send-timeout)`) и ставит `published_at`, затем коммитит. Это осознанное исключение из правила «внешний вызов вне транзакции» (решение 31): блокировки строк нужны, чтобы два экземпляра не отправляли одно событие. Цена: соединение пула и блокировки удерживаются на время отправки. Риск ограничен размером партии и `send-timeout` на событие, а при недоступном брокере проход обрывается на первой же ошибке, то есть занимает соединение не дольше одного `send-timeout`. Альтернатива (выбрать партию, закрыть транзакцию, отправить, отметить отдельной транзакцией) не защищает от одновременной отправки одного события двумя экземплярами без дополнительного состояния «в работе». При первой ошибке проход прекращается: уже подтверждённые события помечены и коммитятся, остальные ждут следующего прохода (порядок не нарушается, брокер, скорее всего, лежит). Доставка at-least-once: событие может уйти повторно, если брокер записал его, а ожидание подтверждения истекло или коммит отметки не удался; потребитель дедуплицирует по `event_id`. Порядок задаёт `created_at`, затем `id`; порядок по моменту коммита между разными переводами не гарантируется, и он не нужен (на перевод одно событие).
41. **Продюсер Kafka: надёжность и ограниченные таймауты.** `acks=all`, `enable.idempotence=true`, `StringSerializer` для ключа и значения. Таймауты заданы явно в `application.yml` (по умолчанию `max.block.ms` 60 с и `delivery.timeout.ms` 120 с повесили бы проход на минуты): `max.block.ms=3000`, `request.timeout.ms=3000`, `linger.ms=5`, `delivery.timeout.ms=5000` (Kafka требует `delivery.timeout.ms >= request.timeout.ms + linger.ms`; тест проверяет это на реальной конфигурации). `app.outbox.send-timeout` (5 с) не больше `delivery.timeout.ms`: тогда событие, по которому ожидание истекло, обычно и не доставлено, а дубль возможен только в редком случае, когда запись прошла, а подтверждение не успело.
42. **Что уходит в Kafka.** Топик `transfers.events.v1` (решение 9). Ключ это `aggregate_id` (id перевода): все события перевода попадают в одну партицию, порядок внутри партиции сохраняется. Значение это JSON события как есть. Заголовки: `event-type` (имя задано контрактом) и `event-id` (id записи outbox; имя пока объявлено константой в `OutboxPublisher`, в `events-contract` его нет: контракт без согласования не расширялся). Топик создаёт бин `NewTopic` (3 партиции, 1 реплика: брокер в проекте один).
43. **Выключатель `app.outbox.enabled`** (`OUTBOX_ENABLED`, по умолчанию `true`) отключает планировщик и создание топика, но не запись в `outbox_events`: события копятся и уйдут после включения. Бин `NewTopic` только при включённой публикации, иначе `KafkaAdmin` в каждом контексте без брокера ждал бы таймаутов (до 30 с). Значения `app.outbox.*` проверяются на старте всегда, даже если публикация выключена (как у `app.pending-retry`). Приложение стартует и работает без Kafka: недоступный брокер даёт предупреждение в логе на каждый проход, события остаются неотправленными. Если брокер недоступен при старте, `KafkaAdmin` может ждать создания топика до 30 с (см. чек-лист в README).
44. **Тесты outbox.** Общий контекст (`IntegrationTestBase`) выключает публикацию (`app.outbox.enabled=false`): в нём нет брокера. Логика publisher проверяется вызовом `runOnce()` с подменённым `KafkaTemplate` (Mockito) на настоящем PostgreSQL: порядок, ключ, заголовки, остановка на ошибке, лимит партии, `SKIP LOCKED`, отметки. Брокер проверяется в единственном дополнительном контексте (`KafkaIntegrationTestBase`: свой Postgres и Kafka на Testcontainers, класс `org.testcontainers.kafka.KafkaContainer`, образ `apache/kafka:4.1.1`): доставка с ключом, заголовками и JSON, отсутствие дублей, сквозной `POST /transfers`, недоступный брокер (продюсер на закрытый порт, сам брокер не останавливается) и отправка после восстановления. Планировщик в этом контексте стоит на интервале в час, проходы вызываются из теста, поэтому результат детерминирован; живой запуск планировщика проверяется вручную. Таблица `outbox_events` общая, тесты чистят её перед собой или ищут свои события по `aggregate_id`.
45. **Известные ограничения outbox.** Нет DLQ, счётчика попыток и пометки «ядовитых» событий: событие, которое брокер стабильно отвергает (например, слишком большое сообщение), блокирует очередь, потому что проход обрывается на первой ошибке, а выборка идёт от самых старых. Опубликованные строки из `outbox_events` автоматически не удаляются (очистка по `published_at`: отдельная задача). Порядок между разными переводами не гарантируется. Транзакционный продюсер Kafka, Avro и Schema Registry не используются: для пет-проекта они избыточны.
